## 기존 PSO 기록과 출력 형식 대조

기존 PID 42596의 성공한 PSO 생성 기록 5,309개를 추가 출력 조사와 VS/PS 해시 쌍으로 대조했다. 129개 PSO가 대응하며 관련 원본 셰이더 51개의 저장된 바이트 해시를 다시 확인했다. 기록 종료의 오류·용량 초과는 모두 0이다. 생성 기록이므로 실제 드로우 실행 또는 현재 게임 상태의 증거로 사용하지 않는다.

- 투명 스칼라 출력에 대응하는 PSO 97개 중 49개의 타깃 2는 `DXGI_FORMAT_R8_UNORM`이고, 48개는 해당 출력 타깃을 선언하지 않는다. R8_UNORM은 [공식 DXGI 정의](https://learn.microsoft.com/en-us/windows/win32/api/dxgiformat/ne-dxgiformat-dxgi_format)의 값 61이며 단일 채널이다. 이 기록에서 해당 출력은 직접적인 부호 있는 XY 객체 MV가 아니다. 어떤 마스크인지와 후속 소비처는 아직 확인하지 못했다.
- 추가 일반 G-buffer 출력의 타깃 3은 8개가 미선언, 8개가 RGBA16_FLOAT, 8개가 RG16_FLOAT다. 같은 출력 계산이 있어도 실제 PSO에서 해당 타깃을 쓰는지는 별개다. float 형식만으로 velocity 리소스라고 판정하지 않는다.
- 원본 census는 타깃 0의 블렌딩 필드만 기록했다. independent blending인 PSO의 타깃 2/3 블렌딩은 이 로그에서 복원할 수 없다. 재질 파일의 기본 blend 설정만으로 엔진의 최종 타깃 상태를 대체하지 않는다.

근거는 `recorded-output-formats.json`이다. 셰이더 출력 번호만으로 투명 스칼라를 배경 MV 감쇠 또는 객체 MV 입력으로 간주하는 경로를 제외했다. 모든 캐시 조합과 실제 타깃 리소스/소비처 연결은 남는다. 새 게임 캡처·설치·GPU 명령은 없다.

## 공통 MV 초기화와 카메라 이력 공급

`0x984000`은 32바이트 노드를 만들고 vtable `0x2b39e80`을 설치한다. +0x8은 실행 함수 `0x7883b0`, +0x10은 `CRenderNode_InitVelocityBuffer` 이름 메서드다. 인접 함수 포인터만으로 추정하던 실행 슬롯을 실제 생성자에 연결했다.

초기화 실행은 context +0x30의 bit 1이 설정된 경우에만 진행한다. node +0x18의 bit 0이 켜지면 velocity 타깃을 `(0,0,0,1)`로 지우고 재투영 드로우를 생략한다. 그 외에는 원본 `velocityBuffer` 키를 타깃 0에 연결하고, `0x61f178d4` 키의 깊이 입력을 픽셀 슬롯 0에 연결한다. 80바이트 상수는 기존 `0xad2254 → 0x1f0114`로 업로드되어 b6에 바인딩된다. 첫 float4의 XY는 view 크기, ZW는 타깃 할당 크기이며 두 PS는 XY만 읽는다. 원본 드로우 래퍼는 상태 검사를 통과했을 때 정점 3개·인스턴스 1개의 호출을 제출한다.

두 PS는 픽셀 좌표에서 깊이 하나를 읽고, 깊이가 float32 `0.9`보다 크면 discard한다. `c=(2*(x/width−0.5), −2*(y/height−0.5))`, `q=M*(c.x,c.y,depth,1)`에 대해 XY 출력은 `(q.xy/max(q.w,0.05)−c)*(0.5,−0.5)`다. 3D 변형은 추가로 `(q.z/max(q.w,0.05)−depth)*1000`을 Z에 쓰고 W에는 0을 쓴다. 객체·본·인스턴스 입력은 없다. 이 경로는 깊이 기반 카메라 MV이며 객체 자체 이동을 보충하지 않는다. W 값의 다른 패스 의미까지 확대하지 않는다.

카메라 입력의 생산은 이미 확인한 원본 프레임 전달에 연결된다. `RenderScene 0x219730 → 0x79aca0`이 선택한 view를 `0x4e4afc`로 갱신한다. view +0x70에는 stride 0x3a0의 카메라 네 개, +0xef0에는 stride 0x190의 이력 네 개가 있다. 원본 생성자 `0x9172c4`도 같은 개수·배치를 사용한다.

- 이력을 유지하는 분기에서는 `0x4e5210 → 0x4e5340 → 0x4e5790`이 기존 카메라를 먼저 저장한다. 이후 `0x4e5104`의 원본 대입이 현재 카메라를 새 값으로 덮는다.
- 이력 writer는 유효성 +0, 정수 위치 XYZ +0x8, 방향 +0x20, 투영 행렬 +0xb0에 기록한다. 초기화 소비부의 view +0xef0/+0xef8/+0xf10/+0xfa0가 이 배치에 대응한다. 위치 차이는 원본 단위 `1/131072`로 변환한다.
- manager 카운터, view의 기록 카운터·상태 및 플래그 조건에 따라 `0x917400`으로 기본 이력을 복원하는 분기가 있다. 해당 기본값은 mutable 전역 저장소이므로 파일의 빈 구간만 보고 실행 중 유효성 값을 0이라고 단정하지 않는다.
- 초기화 소비부에서 유효성 값이 0이면 변환을 identity로 유지한다. 이때 기록되는 픽셀의 XY는 0이지만, discard된 픽셀의 기존 타깃 내용까지 0으로 만든다는 뜻은 아니다.

소비 view의 전달도 정적으로 연결했다. `0x219730`이 `0x1eca90`에 넘긴 프레임에서 virtual +0x20 → +0xfa0 → scene +0x20으로 같은 장면 관리자를 얻어 context +0x20에 저장한다. `0xa86438 → 0xa86498 → 0xa86588`은 컨텍스트를 보유하는 원본 작업에 콜백 `0xa7d164`를 등록한다. 이 콜백은 `0x1ec9b8`에서 원본 48바이트 graph 레코드를 선택한다. `0x1ecf2c`는 그 레코드의 view 인덱스로 manager +0x48 배열을 조회하여 context +0x18에 저장한다. global/null 조건에서는 view를 비운다. 이후 `0x1ec404`가 동일 컨텍스트를 RDX에 두고 노드 virtual +0x8을 호출한다. 초기화 함수의 view 읽기가 이 연결에 대응한다. 컨텍스트 복사는 원본 프레임 참조를 보유하며 별도의 모드 프레임 카운터를 사용하지 않는다.

`audit_native_camera_history.py`는 현재 실행 파일의 함수 23개·지시문 135곳, 원본 leaf 경계, 생성자/vtable/이름, 상수 및 두 PS 디스어셈블리 해시를 검증한다. `native-camera-history.json`에 원본 코드와 연결을 저장했다. 이는 CPU 카메라 갱신·선택·노드 전달과 초기화 입력 계약의 정적 증거다. 실제 graph/view 선택, 다중/생략 view의 GPU 렌더 N-1, 최종 FG 입력 리소스는 추가 확인이 필요하다. 객체별 MV 공급 조사와 구분한다.

## 공통 모디파이어 상수의 업로드와 드로우 바인딩

2026-09-13 원본 `0x1f1208`은 렌더러 전역의 `+0x60` 소유자에서
핸들을 읽어 임시 모디파이어 블록 `+0x1c0`에 저장한다. 기존
`0x56c194` MotionMatrix 공급자가 쓰는 값은 이 블록의 float4 슬롯에
들어간다. `0x1f191c`는 dirty `+0x1c4`일 때 `0x1f088c`로
448바이트를 업로드한 뒤 rigid/skinned 배치를 실행한다. 객체가 바뀌는
조건에서 이전 배치가 새 모디파이어 평가보다 먼저 실행되는 사실은
기존 `native-batch-gate-audit.json`과 함께 해석한다.

업로드 함수 `0x1f08d8`은 핸들의 리소스 플래그에 따라 직접 Map,
동적 업로드, staging 복사를 구분한다. 동적 상수 버퍼의 경우
`0x1f0b1c`가 원본 업로드 풀에서 256바이트 정렬 공간을 받고,
GPU 주소와 크기로 CBV를 만든다. 448바이트 입력의 할당 크기는
512바이트다. CPU에서 원본 업로드 공간으로 448바이트를 복사하며,
이 분기의 종료 함수는 추가 CopyBufferRegion을 기록하지 않는다.
같은 CPU descriptor를 사용하는 바인딩 표를 찾아 dirty 비트를 세운다.
할당 풀의 확장·회수·대기 분기는 이번 조사 범위 밖이므로 모든 상황의
비용이나 동기화 부재를 보장하지 않는다.

공통 바인더 `0x1ed104`는 같은 소유자의 핸들을 논리 상수 슬롯 7,
stage mask 3으로 `0x1f4700`에 넘긴다. 동적 경로는 업로드 함수와
같은 command context `+0x4f8` 핸들 맵의 `+0x28` CPU descriptor를
사용한다. `0x1f3978`은 레이아웃의 상수 항목을 조회해 descriptor
배열에 기록한다. 항목이 `0xff`이면 바인딩을 생략한다.
`0x1f2098`은 `0x1f22e4`의 descriptor 갱신 후
`DrawIndexedInstanced`를 호출한다. 갱신은 `CopyDescriptors`와
`SetGraphicsRootDescriptorTable`로 연결된다. 실제 root parameter는
레이아웃 항목 `+0xe`이며 논리 슬롯 7과 같다고 가정하지 않는다.
이는 [Microsoft의 root table 인자 계약](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-setgraphicsrootdescriptortable)과 일치한다.

실행 중 PID 24404에서 공통 소유자와 핸들 메타데이터만 344바이트
읽었다. 핸들 32742, 크기 448, 플래그 `0x46`을 확인해 이 소유자가
위 동적 상수 경로에 해당함을 검증했다. 소유자 포인터와 헤더를
다시 읽은 결과도 같았다. GPU readback·훅·게임 변경은 없었다.
이 기록은 특정 드로우의 GPU descriptor 내용이나 렌더 N-1 검증이 아니다.

`audit_native_parameter_binding.py`가 원본 함수 16개/지시문 62곳과
SDK 메서드 9개의 x64 배치를 검증한다. SDK의 Windows/non-Windows
구조체 반환 선언은 조건 분기를 선택한 뒤 슬롯 수를 센다.
`native-parameter-binding.json`과
`native-parameter-owner-24404-1789288629228309300.json`에 근거를 저장했다.
재사용 후보는 원본 모디파이어 평가·업로드·바인딩 경로다. 실제 PSO의
b7-to-root 대응, 원소별 이전 입력, GPU N-1 및 투명 패스 선택은 남는다.

후속으로 기존 캡처의 원본 MV VS와 바이트 해시가 일치하는 root 기록
152개를 [공식 D3D12 역직렬화 API](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-d3d12createversionedrootsignaturedeserializer)로 읽었다.
고유 VS 23개/고유 root 바이너리 1개이며 모두 vertex-visible space 0의
b7이 root slot 3에 들어 있다. 별도로 저장된 `layouts.csv` 전체 항목도
API 결과와 일치했다. 해당 슬롯의 바인딩 4,745건은 모두 타입이 맞고
핸들이 0이 아니었다. 23개 중 이전 계산에서 MotionMatrix를 읽는 것은
21개/기록 140개다. 나머지 2개도 b7을 읽지만 이력을 같은 방식으로
사용한다고 집계하지 않는다. 이 범위의 b7-to-root 선언 대응은 확인됐다.
현재 프로세스의 descriptor 내용·공통 소유자 핸들과의 실제 대응은
확인되지 않았으며, 899개 전체의 실행 검증으로 확대하지 않는다.
`audit_recorded_native_roots.py`와 `recorded-native-root-audit.json`에
입력 해시와 각 기록의 대응을 저장했다. 게임 연결·새 캡처는 없었다.

MotionMatrix 공급에서 읽는 proxy `+0x9e` 가중치도 생성자까지 연결했다.
mesh 생성자 `0x236bd0`은 공통 생성자 `0x237518`을 호출한 뒤 실제
mesh vtable `0x2ac22a0`을 설정한다. 공통 생성자의 기본값은 255다.
원본 입력의 type byte `+0x60`이 1/5/7/12일 때는 float `+0x80`을
0~1로 제한하고 255를 곱한 뒤 정수로 잘라 가중치에 저장한다.
원본 상수 0/1/255, type 검사 leaf 전체 26바이트와 mesh 생성자 연결을
검증했다. `0x56c194`는 0에서 현재 변환을 쓰고, 유효 이력과 255에서
이전 변환을 쓰며 중간값에서는 분해/보간을 수행한다. 가중치를 이력의
존재 여부나 정확한 렌더 N-1 판정으로 사용하지 않는다. 입력 float의
상위 생성/공개 속성명과 중간값의 전체 수치 동작은 아직 미확인이다.

## 객체 조건 마스크에서 원본 technique 선택까지

기존 그룹 제외 검사에서 관찰한 `0x20`은 드로우 패스 번호로 직접 사용되지 않는다. `0x1e9228`이 만든 마스크는 `0x1e9b88`의 일반 객체 및 중첩 그룹 분기에서 같은 `0x1ea24c`로 전달된다. 이 함수가 재질 구간별로 호출하는 `0x1ea780`은 마스크를 여섯 번째 인자로 받고, 재질 소유자 +0x7f8의 조건표를 `0x1e9078`로 조회한다.

조건표 조회는 입력의 각 비트에 대응하는 24바이트 항목에서 필수 조건·출력 집합·조합 인덱스를 누적한다. 조합이 있으면 별도 표를 조회하고, 필수 조건이 입력 마스크에 모두 포함되지 않으면 출력 전체를 비운다. 단일 비트 입력에는 +0x2e0의 유효 비트와 +0x228의 빠른 조회표가 있다. 반환된 집합의 각 비트는 `0x1eb7bc`의 technique 확장에 전달되며, `0xaf38f0`은 같은 소유자의 +0x7d8 배열과 +0x7e4 개수를 사용한다. 따라서 입력 비트 5와 출력 인덱스 5를 동일시하지 않는다.

조건표 생산은 `0x228420`에서 연결된다. 원본 material interface의 virtual +0x90이 반환한 64비트 마스크 배열과 개수를 `0x228fd8`에 넘긴다. 이 함수는 23개 입력 비트의 관계를 미리 변환하고, 조회표 및 단일 비트 빠른 경로를 만든다. 초기 생성 `0x228054`와 재설정 `0x22a36c`의 같은 소유 필드도 연결했다. 원본의 사전 계산·재사용 구조이며, 모드에서 매 드로우에 이 표를 다시 만들 근거는 없다.

원본 함수 16개/지시문 64곳을 검증했다. 게임을 열지 않는 독립 검사에서는 변경하지 않은 `0x1e9078`을 소유 메모리의 작은 표로 실행했다. 비트와 출력 인덱스 차이, 여러 비트의 결합, 누락 조건 거부, 조합표, 단일 비트 빠른 경로 등 8개 경우가 모두 일치했고 입력 표도 보존됐다. 이는 표의 해석 검사이며 실제 게임의 선택표나 GPU 드로우 검증은 아니다.

별도로 추출된 원본 `.mt` 381개의 technique 1,222개를 전수 대조했다. `featureFlagsEnabledMask`에 `0x20`이 포함된 항목에는 G-buffer velocity 90개, hair velocity 6개, 별도 velocity 16개 패스가 있다. 같은 technique의 피부 투과·머리카락·투명 보조 패스도 포함되므로 단일 MV 패스 전용 비트로 설명하지 않는다. 예를 들어 원본 multilayered는 mask 1에서 일반 G-buffer, 33에서 G-buffer velocity를 선언하며, 524289/524321 쌍도 같은 차이다. 추출된 base 재질 범위이며 활성 모드 및 모든 캐시 항목을 포함한다는 주장은 하지 않는다.

공식 SDK의 [CMaterialTemplate](https://github.com/WopsS/RED4ext.SDK/blob/master/include/RED4ext/Scripting/Natives/Generated/CMaterialTemplate.hpp)과 [MaterialTechnique](https://github.com/WopsS/RED4ext.SDK/blob/master/include/RED4ext/Scripting/Natives/Generated/MaterialTechnique.hpp)는 technique 배열과 조건 마스크 필드를 정의한다. 현재 공식 파일도 대조했다.

후속 조사에서 미확인이던 virtual +0x90 구현을 연결했다. 원본 `CMaterialTemplate` 이름과 크기 0x1a0를 등록하는 `0x5abcf8`의 RTTI vtable +0xd8은 `0xca6e8c → 0xca6e94` 생성자로 연결된다. 생성자는 객체 +0x78에 렌더 인터페이스 vtable `0x2b88450`을 설치한다. 이 테이블의 +0x90은 `0x228f1c`, +0x88은 `0x2299a4`, +0x98은 `0x18e64f0`이다. RTTI의 ConstructCls 슬롯은 [공식 RTTITypes.hpp](https://github.com/WopsS/RED4ext.SDK/blob/master/include/RED4ext/RTTITypes.hpp)와 함께 대조했다.

- 조건 마스크 공급 `0x228f1c`: 인터페이스 +0xf8/+0x104는 실제 재질 +0x170/+0x17c의 technique 배열·개수다. 원본 32바이트 technique의 +0x10을 읽어 출력 배열의 같은 인덱스에 64비트로 기록한다. 정렬이나 원소 재배치는 없다.
- 개수 공급 `0x18e64f0`: 동일한 인터페이스 +0x104의 개수를 반환한다. `0x229790`은 이를 렌더 재질 +0x1bc에 기록하고 같은 개수의 패스 목록 배열 +0x7d8을 준비한다.
- 패스 공급 `0x2299a4`: `0x229790`이 0부터 순회하는 동일한 technique 인덱스를 받는다. 원본 32바이트 technique의 패스 배열을 104바이트 stride로 읽고 120바이트 확장 레코드로 옮긴다. regular/discarded 이름은 원본 +0/+8에서 확장 +0x58/+0x60으로 전달한다. 레이아웃은 [공식 MaterialPass.hpp](https://github.com/WopsS/RED4ext.SDK/blob/master/include/RED4ext/Scripting/Natives/Generated/MaterialPass.hpp)와 일치한다.

추가 독립 검사는 `0x228f85..0x228fb3`의 원본 추출 루프를 그대로 실행했다. 추출된 381개 재질의 마스크 배열과 빈 배열/최상위 비트/64개 서로 다른 원소의 세 경계 조건을 합쳐 384개 모두 값·순서가 일치했다. 입력 재질/technique 저장소와 출력 앞뒤 영역도 보존됐다. 이 검사는 이미 확보한 저장 공간의 복사 루프이며 원본 할당·크기 변경이나 실행 중 재질 수명을 시험한 것은 아니다.

따라서 원본 CMaterialTemplate 구현에서는 조건표 입력과 확장 패스 목록의 인덱스 대응을 확보했다. 다른 material interface 구현, 실제 그룹 드로우가 선택하는 재질/technique, 원소별 이전 입력과 렌더 N-1은 남아 있다. 플래그를 강제로 켜면 모든 배열 MV가 올바르게 나온다고 판정하지 않는다.

## 객체 이력과 LOD 선택 이력의 구분

`0x1e9228`은 객체의 기록된 갱신 번호가 현재 번호와 같으면 virtual +0xf0 호출을 생략한다. 다르면 기록 번호와 현재 번호−1을 비교한 boolean을 넘긴다. 확인된 mesh vtable `0x2ac22a0`의 해당 슬롯은 `0x1e8778`이다. 이 boolean만으로 이전 변환의 유효성을 인정하지 않는다.

일반 객체 분기는 `0x1e8b48`에서 거리·LOD 임계값·원본 플래그를 평가한다. 이후 `0x2949bc`가 세 LOD 선택과 상태 비트, 시점 값을 작은 정수 레코드에 기록한다. LOD 번호+1은 bit 1·4·7의 각 3비트 구간에 들어간다. `0x1e99c4`는 같은 구간을 해석하고 현재 시점과의 차이에 따라 드로우할 선택을 반환한다. 이것은 위치 행렬 저장소가 아니다. 원본 객체의 이전 변환은 별도로 확인한 virtual +0x88/+0x90 → `0x1e54c8` 경로다.

배열 그룹 분기는 `0x2dc468`에서 각 현재 원소의 위치와 카메라 거리를 평가하고 LOD 상태별 원소 목록을 갱신한다. 여기에서도 `0x1e99c4`와 `0x294138 → 0x2949bc`를 공유한다. 원본 소스 배열 인덱스가 16비트 값으로 그룹의 +0x18 목록에 들어가며, `0x1e8778`은 그 값을 읽어 프록시 +0x108 배열의 해당 48바이트 현재 변환을 +0x40의 재배열 저장소에 추가한다. 전역 배열 경로에서는 `0x3cc59c`로 해당 구간을 기록하고 그룹 +0x50에 출력 시작 인덱스를 보관한다. 출력 순번을 원본 배열 인덱스와 동일시하지 않는다.

그룹 소유자의 +0x30에는 원본 배열 원소당 4바이트의 LOD 메타데이터가 있다. `0x2de168`은 프록시 +0x70으로 그룹 소유자를 조회하고 현재 원소 수와 +0x3c를 비교한다. 크기가 다르면 `0xb740d0`으로 조절한다. 이 함수는 새로 늘어난 항목만 초기화하며 기존 구간은 유지한다. 따라서 같은 원소 수나 같은 메타데이터 주소가 같은 객체·이전 위치를 증명하지 않는다. 다른 변경·초기화 경로는 추가 확인이 필요하다.

`audit_engine_history_sources.py`를 확장하여 기존 이전 변환 공급과 이번 선택 경로를 함께 검증했다. 현재 실행 파일의 함수 23개/지시문 139곳 및 기존 vtable과 원본 독립 검사 해시가 일치한다. 이 결과로 virtual +0xf0의 연속성 조건과 그룹 메타데이터를 이전 변환 후보에서 제외한다. 실제 그룹 선택 재질·원소별 이전 입력·GPU N-1·최종 MV 출력은 미확인이다. 게임이나 제품 DLL을 변경한 결과가 아니다.

## 기존 미분류 23개 투영의 분기별 분석

기존 분석은 출력의 전체 의존성에서 카메라 행에 곱해지는 XYZ를 하나씩 찾았다. 머리카락 5개, flat_tire_multilayered 16개, long_distant_vehicles 2개는 출력 phi가 여러 정점 위치 중 하나를 선택하므로 이 기준을 통과하지 못했다. 이들의 이전 입력 추적 자체가 실패한 것은 아니다.

추가 도구는 실제 출력부터 직접 카메라 곱셈·덧셈과 phi를 따라간다. phi의 join/선행 블록을 보존하고 XYZW 네 성분이 같은 분기를 선택하는지 검사한다. 카메라 계수 중복이나 서로 다른 XYZ를 임의 합성하지 않는다. 각 분기에 원본 정점 SSA, 입력·리소스 의존성, 선행 제어 흐름을 기록했다. 원본 바이트코드와 분기를 수정하지 않는다.

- 머리카락 5개와 타이어 16개는 현재 투영 2개, 이전 투영 1개다. 추가 현재 변형 분기를 이전 변형에도 똑같이 적용했다고 가정하지 않는다. 머리카락의 조건부 현재 위치에는 b0/b4 의존성이 추가되고, 타이어 변형에는 원본 위치·재질/차량 값과 비교/삼각함수 등이 연결된다. 이 사실만으로 해당 원본 MV가 정확하거나 잘못됐다고 판정하지 않는다.
- 원거리 차량 2개는 현재 투영 2개, 이전 투영 2개이며 양쪽이 같은 join의 선행 블록을 선택한다. 서로 다른 선행 블록의 현재·이전을 교차 결합하지 않는다. 한 현재 분기는 정점 입력/일반 리소스 읽기 없이 b1[37] 상수의 음수 XYZ를 카메라로 투영한다. 이 분기의 좌표를 독립 이동 정점으로 해석하지 않는다. 조건은 원본 텍스처 표본과 입력 인덱스 비교를 포함하며 실제 가시성과 생산 입력은 추가 확인한다.

23개 모두 카메라 행과 정확한 분기별 XYZ를 추출했고 오류는 0개다. 기존 872개/4개 단일 투영 결과와 합쳐 확보된 899개 VS의 투영 형태를 설명하지만, 모든 원본 MV 생산자/현재·렌더 N-1의 검증 완료를 뜻하지 않는다. 현재·이전 SSA가 다르다는 것은 실제 값이 다르다는 증거가 아니다. `native-projection-branches.json`은 기존 미분류 기록을 지우지 않는 보충 근거다.

## 원본 본 이력 공급의 구체적 연결

1. `0x612950`이 manager +0xe6108에 원본 리소스 핸들을 만들고, 별도 CPU 저장소를 +0xe6040에 둔다. 리소스 시작 48바이트에는 기본 변환을 기록한다.
2. `0x3a6e64`가 객체 포인터를 보유하는 48바이트 항목을 할당한다. 핸들은 원본 인덱스와 세대를 포함한다. `0x3a7334`는 해제 시 세대를 증가시키고 네 저장 구간을 반환한다.
3. `0x215dd8 → 0x215e5c`는 객체 +0x10 핸들과 본 수×48바이트로 쓰기 구간을 예약하고 원본 대기열에 핸들/오프셋/크기를 기록한다. 대기열 한도는 4,096이다.
4. 원본 갱신 호출부 `0x29401c → 0x293498`이 대기열을 옮긴다. `0x20a958`이 항목별 링 슬롯에 새 구간을 적용한다. `0xa7dd14` 복사 작업은 원본 리소스에 CPU 구간을 복사한다. 이 원본 복사를 모드에서 중복할 이유는 현재 확인되지 않았다.
5. `0x20a958`은 `(cursor-1)&3`, `(cursor-2)&3`를 선택한다. 보존 개수가 1 이하이거나 reset 비트가 있으면 현재 구간을 재사용한다. 이전 구간을 쓰는 분기에는 크기 일치 검사가 있다.
6. `0x20b1ec`가 같은 본 객체의 +0x14/+0x18/+0x1c/+0x20에 현재 오프셋, stride 48, 이전 오프셋, 두 오프셋이 다른지를 기록한다. 서로 다른 오프셋이 정확한 렌더 N-1이나 서로 다른 포즈를 증명하지는 않는다.
7. 공통 드로우 준비 `0x1f1208`은 기존 드로우 거부 검사를 통과하면 전역 manager를 통해 슬롯 10/stage 0 바인더 `0x292360c → 0x1f5438`을 호출한다. 마지막 함수는 현재 셰이더 레이아웃으로 슬롯을 변환하고 리소스 디스크립터와 dirty 상태를 기록한다. 레이아웃에 슬롯이 없으면 기록하지 않는다.

이 경로는 새 본 저장소나 픽셀 추정기를 설계할 출발점이 아니라 원본 리소스·메타데이터를 재사용할 근거다. 갱신 및 작업 완료 시점, D3D 디스크립터, 그룹별 메타데이터와 정확한 렌더 N-1은 아직 연결해야 한다.

## 이전 정점의 원본 compute 생산과 상수 바인딩

`0x1f5b24`는 공통 상수 블록에 논리 행을 기록한다. 행 번호가 6보다 크면 dirty bit 0을 표시한다. 원본 `0x1f27c0`은 정적 범위 상수 7~17을 읽고 블록 +0x70부터 176바이트를 복사한다. 256바이트로 정렬한 디스크립터를 만들고 stage 0/type 2/slot 3 바인더에 넘긴다. 따라서 이전 정점용 논리 행 8·9·10은 b3 행 1·2·3이다. 원본 t9 사용 VS 233개 모두 같은 세 행을 읽는다. 초기 10개 후보에서 미확인이던 논리 행과 셰이더 행의 연결을 정적으로 해소했다.

드로우 준비 `0x1f1208`은 `0x23a1a0`이 반환한 객체의 +0x28 값을 전달한다. 반환 경로는 원본 interface virtual +0x20의 결과에서 +0xfa0를 읽는다. 변형 정점 생산 측 `0x76c11c`/`0x76d944`에도 같은 접근 순서가 있다. `0x1f2b68`은 전달값의 홀짝을 구하고, `0x76d868`은 해당 chunk의 현재 슬롯과 반대 슬롯의 이전 핸들·scale/offset을 선택한다. 같은 접근 순서는 실제 view/object 주소 일치 또는 렌더 N-1의 증거를 대신하지 않는다.

생산 경로는 원본 view 플래그 +0x30의 bit 1 및 feature `0x1d`를 검사한다. 드로우 공급부도 feature `0x1d`를 검사한다. `0x76e184`는 원본 chunk 조건을 통과한 버퍼의 양쪽 parity 슬롯을 원본 복사 함수로 초기화한다. `0x76d944`의 stage 2는 현재 parity의 scale/offset을 저장한다. mesh virtual +0x30이 false인 분기에서는 원본 UAV와 본 버퍼(compute t2), 상수를 연결한 뒤 compute를 실행한다. true인 타입은 stage 0의 원본 정점 구간 복사 분기를 사용한다. 아래 동시 기록에서 이 차이를 추가 확인했다. 초기화 플래그·카운터·culling/LOD와 실제 GPU 실행 계약은 더 검증해야 한다.

`0x76e378` 및 해당 cold 분기의 원본 키를 정적 캐시의 길이 있는 이름과 FNV 해시, CS identity에 연결했다. `m_computeSkinning_MeshSkinned`와 `m_computeSkinning_GarmentMeshSkinned`는 같은 CS 해시다. 확장 스키닝과 확장 의상도 같은 CS 해시이며 MeshStatic은 별도 CS다. 5개 이름이 실제로는 3개 계산 프로그램을 공유한다. 이를 의상에 추가 변형이 전혀 없다는 뜻으로 확대하지 않는다. 원본 MV 그래프에는 별도 t77/모디파이어 의존성도 남아 있다.

## 변형 프로그램 전수 키 연결과 DXR 소비 경로 구분

정적 캐시에서 길이 접두부, 이름 해시와 프로그램 identity를 대조해 식별한 `m_computeSkinning_*` 이름은 37개, 고유 CS는 27개다. 기존 5개 외에 positions-only, batched, 단일 본, 의상, 차량, SpeedTree, tarps, VerMov 및 pass-through 변형이 포함된다. 원본 `0x2930410`은 16개 기본 키와 각각의 HalfFloat 키를 선택한다. HalfFloat 키는 직접 상수가 아니라 boolean의 NEG/SBB 결과에 차이 마스크를 AND하고 기본 키를 더한 값이다. 16쌍 모두 캐시 이름 해시와 일치했다. 기존 `0x76e378`/cold 분기까지 합치면 식별한 37개 이름 모두 선택 코드에 연결된다. 캐시 파서는 전체 형식 파서가 아니며 거부된 이름도 별도로 유지한다.

새 선택부의 상위 경로 `0x1d56350 → 0x292263c → 0x291f968 → 0x2930410`과 출력 소비처를 추적했다. `0x291df88`이 소유자 +0x17804의 공용 버퍼를 만들거나 재사용한다. `0x291f968`은 컨텍스트 +0x1e158에서 정점 수×stride 구간을 예약하고 용량 초과 시 실패를 반환한다. stride는 +0x1e14c가 0이면 12, 아니면 8바이트다. 버퍼 핸들·오프셋·stride를 원본 geometry 레코드 +0x8/+0x18/+0x1c에 기록한다.

같은 상위 함수가 컨텍스트를 `0x291f6fc`로 확정하고 `0x2a40df4 → 0x2a417d0 → 0x2a419c8`이 이 레코드를 GPU 주소와 정점 stride로 변환한다. 일반 분기의 원본 command-list vtable +0x240 호출과 인자 배치는 SDK의 `BuildRaytracingAccelerationStructure`와 일치한다. 이 API는 GPU에서 레이트레이싱 가속 구조를 구축한다. [Microsoft 공식 문서](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist4-buildraytracingaccelerationstructure)

따라서 이 공용 변형 정점 생산자의 DXR 소비 경로는 확인했다. 이를 래스터 MV의 t9 이전 정점 생산자로 집계하지 않는다. 원본 변형 계산의 재사용 후보로 보존하되, 이전 프레임 보존·추가 소비처·실시간 실행과의 연결은 미확인이다. vendor 확장 분기와 대체 geometry 형식도 별도 미확인으로 유지한다. 아래 래스터 노드 식별까지 포함해 함수 12개 및 지시문 44곳의 검증 근거를 `native-deformation-consumer.json`에 저장했다.

별도 래스터 생산부 `0x76c11c`의 원본 노드는 `CRenderNode_ComputeSkinningAndTangentUpdates`다. 생성 함수 `0x1505d78`이 설치하는 vtable `0x312db80`의 실행 슬롯 +0x8과 이름 메서드 +0x10을 대조했다. 이 노드는 view 플래그/feature 검사 뒤 후보 목록을 읽고, 유효한 원본 chunk 번호로 owner +0x60의 카운터 배열을 조회한다. 저장된 값이 현재 장면 +0x28과 같으면 생산 전에 중복 작업을 건너뛴다. 아래 동시 기록은 이 노드의 실제 실행 조건·후보 수·chunk 갱신 기록까지 추가한 증거다. 모든 타입/장면 및 GPU 실행을 증명하지 않는다.

## 실제 이전 정점 슬롯 선택 기록

PID 24404의 원본 `0x76d868`에 연결한 제한된 CPU 진단에서 228건을 기록했다. 장면 카운터는 508126~508201의 연속 76개이며 소유자 2개/chunk 조합 3개다. 전부 드로우 공급 호출자 `0x1f2b68`에서 왔다. 228건 모두 전달 parity가 장면 카운터의 홀짝과 일치하고, descriptor의 이전 핸들은 반대 parity 슬롯이었다. 현재/이전 핸들은 모두 달랐다.

이 구간에서는 `0x76d944` 생산 측의 같은 선택 함수 호출이 관찰되지 않았다. 이를 GPU 생산이 없다는 증거로 사용하지 않는다. 선택 함수 이전의 실행 조건, 장면 목록/중복 처리 또는 다른 생산 경로를 조사해야 한다. 핸들의 교대 선택은 실제 내용의 갱신이나 정확한 렌더 N-1을 증명하지 않는다.

진단은 최대 8,192건이며 GPU 복사/명령을 추가하지 않는다. DLL은 `preskin-selection-probe-a19dd72aef01/observer.dll`, SHA-256은 `de0977ae1abca720715b7e182bcb411bb845557eb996e7ed071d75654c5627e3`이다. 기록 종료 후 프로세스 수명 동안 원본을 전달한다. 호출자 스택 오프셋은 원본 함수 전체 바이트로 검증한 진단 전용이며 제품 호환 경로로 채택하지 않는다. 새 MV/FG 변경은 없다.

## 노드·생산·드로우 동시 기록과 원본 복사 분기

이후 PID 24404에서 같은 선택 진단을 재사용하고 노드/원본 단계 진입 두 곳을 함께 기록했다. 노드 156회 중 78회는 view 플래그 조건을 통과했고 후보가 각 2개였다. 이 78회에서 후보 카운터는 실행 전 현재 장면과 달랐고 실행 후 같아졌다. 원본 단계 0~4는 각각 156회, 합계 780회 호출됐다. 나머지 78회는 해당 view 비트가 꺼져 있고 후보 수가 0이었으며 생산 단계를 호출하지 않았다. 실제 호출자는 모두 `0x1ec46d`였다.

생산 측 선택 740건은 같은 스레드의 노드 진입/종료 시각 구간에 각각 하나씩 포함됐고 장면 카운터도 모두 일치했다. 드로우 444건은 같은 소유자/chunk/장면의 원본 생산 5단계 선택 뒤에 호출됐으며 현재/이전 핸들이 같았다. 연속 장면 쌍 146개에서는 이번 이전 핸들이 직전 현재 핸들과 일치했다. 캡처 경계의 드로우 2건과 다른 소유자의 드로우 74건에는 생산 대응이 없었다. 이 미대응을 제외하고 전체를 성공으로 집계하지 않는다. CPU 기록 시각은 GPU 실행/완료 시각이 아니다.

관찰된 mesh 주소의 후속 읽기에서는 vtable `0x2e73278`, virtual +0x30 대상 `0x496010`을 확인했다. 원본 생성자 `0x376310`도 같은 vtable을 설치하며 해당 메서드는 상수 true를 반환한다. 이 타입의 `0x76d944`는 stage 0에서 원본 정점/부가 스트림 구간을 현재 parity 버퍼로 복사하고, stage 2에서는 scale/offset 저장 후 compute 분기 전에 반환한다. 원본 복사 함수 `0x6197b4`의 리소스·offset·크기 전달과 command-list vtable +0x78은 `CopyBufferRegion`의 SDK 배치에 대응한다. [Microsoft 공식 문서](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-copybufferregion)

따라서 생산 단계 호출을 compute 실행으로 해석하지 않는다. 기존 원본 복사로 채워지는 이전 정점 이력도 재사용 후보에 포함한다. 후속 mesh 읽기는 호출 중 타입/수명 기록이 아니므로 모든 stage의 실제 분기를 확정하지 않으며, 복사 원본의 생산자·GPU 순서·내용·정확한 렌더 N-1을 추가 확인한다. 별도 모드 복사를 추가한 결과가 아니다.

노드 진단은 최대 256회/후보 1,000개 순회/단계 표본 16개로 제한했다. 실제 이미지나 GPU 버퍼는 복사하지 않았다. 독립 입력의 유효/무효 경로, 후보 제한, 갱신 전후 비교, 5단계 전달 및 원본 반환 보존 검사를 통과했다. DLL `preskin-node-probe-b066975b5c6c/observer.dll`의 SHA-256은 `b6e4f2025341b9dd97caf18b7582ccffae96023debcd21e1d9d77aad9b198c9c`이다. 양쪽 기록은 종료했고 DLL은 원본을 전달한다. 게임은 기록 후 응답 중이었다. 장시간 안정성 또는 새 MV/FG 적용을 주장하지 않는다.

## 복사 원본의 정점 갱신 명령과 두 종류의 이력

관찰된 복사 타입의 원본 소스 생산 경로를 `UpdateClothMeshData` 명령까지 연결했다. `0xc43b50`은 전역 렌더러 virtual +0x450으로 기존 명령 소유자를 얻고 virtual +0x228에 객체 참조, chunk 번호, float3 배열과 bounds를 전달한다. 원본 소유자 vtable의 해당 슬롯은 `0xc43bc8`이다. 직접 확인한 상위 호출 함수는 `0x13d848`, `0x40c714`, `0x2402618`이며, 변형 위치/배열 변환과 bounds 계산 후 같은 경로를 사용한다. 상위 시뮬레이션 종류와 모든 객체 타입을 확정한 것은 아니다.

`0xc43bc8`은 원본 명령 이름과 vtable `0x2b7d940`을 설치하고 기존 객체별 63개 버킷 경로에 112바이트 명령을 예약한다. 배열 전달 함수 `0x1c7a60`은 포인터·count·capacity를 옮기고 원본 배열을 비운다. 이 전달 자체를 정점 전체 복사로 계산하지 않는다. 명령은 객체 참조를 보유한다. 실행 슬롯 +0x8은 작은 함수 `0x6d40b0`이며, 명령 포인터에 +0x20을 더한 뒤 `0x6d40bc`로 점프한다. 이 작은 함수에는 unwind 기록이 없어 기존 직접 CALL 검색만으로는 연결이 나오지 않았다. 원본 테이블과 명령 생성 코드를 함께 대조했다.

1. 실행부는 보유 객체 +0xd8의 mesh와 같은 명령의 chunk·위치 배열·bounds를 `0x6d4168`에 전달한다.
2. `0x6d4168`은 half extent `(max-min)*0.5`와 midpoint를 기록하고 원본 chunk offset으로 mesh +0x1c0의 CPU 저장 구간을 선택한다. 위치는 `(p-midpoint)/halfExtent*32767`의 정수 변환으로 XYZ를 16비트씩, W를 32767로 기록한다. 정점당 8바이트다. 상수 0.5와 32767은 실행 파일의 실제 데이터를 확인했다.
3. mesh +0x1e8의 dirty bit 0x20을 설정하고 `0x6d42d4`가 원본 renderer +0x4c80 목록에 보유 참조를 넣는다. 잠금은 +0x4c78이다.
4. 기존 `RenderFrameTick`의 `0x209234`가 같은 목록을 분리하고 잠금을 해제한 후 `0xca930c`를 호출한다. 앞서 연결한 원본 명령 소비와 렌더 갱신 순서를 재사용하는 경로다.
5. `0xca930c`는 dirty일 때만 두 GPU 핸들 mesh +0x1e0/+0x1e4의 선택을 교대한다. 기존 current 양자화 bounds를 previous로 옮기고 새 bounds를 current로 적용한다. 원본 업로더 `0x220068`에 CPU 구간을 넘긴다. 초기 bit 0x10이 있으면 반대 버퍼에도 같은 데이터를 먼저 넣어 양쪽을 초기화한다.
6. 같은 갱신이 chunk descriptor에 현재 정점 핸들·bounds와 이전 핸들 +0x84, 이전 scale/offset +0x50/+0x60을 기록한다. 초기 chunk 연결 `0x11ac3d0`은 이전 offset +0x88도 기록한다. 이는 원본 draw/이전 정점 공급에서 사용하는 descriptor 구조와 연결된다.

여기서 **소스 mesh의 데이터 갱신 이력과 장면 카운터 기반 preskin 렌더 이력은 별개**다. 소스는 dirty 명령이 없으면 교대하지 않는다. 따라서 소스의 반대 핸들을 언제나 정확한 렌더 N-1로 해석하지 않는다. 기존 preskin의 원본 복사·선택 경로가 렌더 간 이력을 어떻게 유지하는지까지 검증한 뒤 재사용한다. 새로운 모드 전체 복사나 별도 CPU 위치 캐시를 추가한 결과가 아니다.

실행 파일의 함수 18개, 작은 진입점 2개, 지시문 42곳과 vtable/이름/실수 상수 대조를 `native-cloth-history.json`에 저장했다. 이번 증거는 정적 연결이다. 실제 명령 입력, GPU 내용·완료와 렌더 N-1, 상위 시뮬레이션/LOD/토폴로지 변경, 이전 캡처의 미대응 owner는 남아 있다. 명령 이름만으로 모든 의상 또는 의상만 이 경로를 쓴다고 판단하지 않는다.

## 원본 모디파이어 분기와 추가 변형 공급

`0x1f055c`의 실제 정수 비교/분기를 0~31 모두 평가했다. 32 ID는 30개 진입점으로 연결되며 기존 생성자 목록과 일치한다. 15·16·19는 같은 원본 no-op 반환 함수다. 30·31은 별도 공급부로 전달하는 작은 래퍼다. 0은 context의 virtual +0x20으로 전달하며 실제 대상은 미확인이다. 32분기를 열거했다는 사실은 모든 변형 생산자나 프레임 유효성을 확인했다는 뜻이 아니다.

공급 실행 조건도 별도다. `0x1f0418`은 이미 생성된 모디파이어 레코드를 순회하고 `0x1f04a8`의 갱신 분류 마스크와 호출자 마스크를 AND한다. 이 값은 캐시의 `1<<enum` 요청 비트와 다르다. 원본 MotionMatrix·재질·차량·거리 조건은 분류 4, 의상은 1, 파괴는 7이다. 공통 드로우 `0x1f1208`은 객체 인덱스가 바뀌면 5, 지오메트리 입력을 갱신하면 추가로 2를 설정하며, 드로우 패킷의 분류 비트도 검사한다. 두 번째 직접 호출부 `0x62331c`도 별도 마스크를 유지한다. 기존 값 재사용과 새 값 공급의 원본 조건을 모드에서 무조건 매 드로우 실행으로 바꾸지 않는다.

원본 `0x3a0e54`는 객체 프록시 +0x48의 확장 데이터 목록을 조회한다. 각 항목의 virtual +0x8 결과를 원본 타입 포인터와 비교한다. `0x57c9c0`은 같은 목록에서 기존 항목을 재사용하거나 원본 타입 시스템으로 생성한다. 이 생성 함수의 원본 잠금·할당을 모드의 매 드로우 경로로 복제하지 않는다.

- 의상: `0x236bd0`의 분기가 원본 chunk 데이터로 `0x375a68`을 호출하고 확장 데이터의 16바이트 항목 배열에 핸들을 보관한다. `0x375a68`은 원본 소스별 캐시와 참조 수를 사용한다. 공급부 `0x3a09b4`는 실제 드로우의 chunk 번호를 범위 검사한 뒤 같은 배열의 핸들을 `0x1f3a6c`에 넘긴다. 유효성 0/1만 b7의 IsBound 행에 기록한다. 원본 핸들과 원본 정점/본 입력의 재사용 후보이며 별도 CPU 복사를 요구하는 증거는 없다.
- 차량: 원본 `UpdateVehicleParams` 명령의 vtable 항목이 `0x57c800`이다. `0x57d968`은 객체를 보유하고 24바이트 payload를 명령으로 전달한다. `0x57d9f4 → 0x57cacc`는 원본 객체별 명령 구간을 선택하고 2,048바이트 블록에 80바이트 레코드를 예약한다. 실행부가 확장 데이터 +0x10~0x24에 쓴 두 float3를 `0x3a0f60`이 그대로 읽고 `0x3a0e90`이 pivot/grid의 b7 두 행에 기록한다. 대기열 소비와 렌더 프레임 순서는 미확인이다.
- 파괴/분리: `0x57bec8`의 cold 분기는 확장 데이터 +0xc0의 소유자를 생성/재사용한다. 원본 `0x2923b40`이 512바이트 리소스를 만들고 `0x2923b9c`가 원본 데이터와 count/상태를 갱신한다. 공급 시 `0x2923c34`는 dirty일 때만 512바이트를 업로드한다. `0x2a2be74`의 DismParams는 count와 두 상태 플래그다. 이전 객체 행렬이 아니다. CullObjectsCB는 별도 리소스 바인딩이고 DismParams는 b7 상수 행이다.
- 재질: `0x57c92c`가 payload 비트에 따라 원본 7개 float4 중 필요한 값만 갱신한다. `0x3a0bb0`은 같은 확장 데이터에서 해당 값을 읽고 `0x3a0afc`가 선언된 행에 기록한다.

현재/이전 위치 그래프의 모디파이어 로드도 비교했다. DismParams 323 VS, 의상 IsBound 226 VS, 재질 파라미터 195 VS, 거리 조건 8 VS는 같은 SSA 로드를 공유한다. 차량 25개 중 24개도 같은 로드다. 이들 상수에 각각 새로운 이전 프레임 저장소가 필요하다고 가정하지 않는다. 이는 정적 데이터·제어 그래프 비교이며 같은 위치/포즈 또는 정확한 N-1을 뜻하지 않는다. 본·정점·객체 변환의 시간 대응은 별개다.

## 원본 명령 소비와 객체·본 갱신 작업 연결

상위 원본 함수 `0x29384c`가 앞서 분리해서 조사한 명령 대기열, 장면 객체 배열, 본 갱신을 연결한다. 객체 크기 0xcb8의 원본 생성자와 vtable 슬롯 2까지 확인했다. 렌더러 초기화는 이 객체를 +0x70에 보관한다. 아래 실시간 진단에서 현재 경로의 간접 호출자를 확인했다. 모든 호출 주기와 예외 검증은 미완료다.

1. `0x29401c`로 원본 본 갱신 입력을 확정하고, 기존 완료 의존성을 가진 작업 컨텍스트를 만든다.
2. 원본 `RenderFrameTickResetPools` 작업을 등록하고 다음 의존성 그룹으로 전환한다.
3. `0x39d2fc`가 원본 명령 블록을 분리한다. 객체 추가·삭제와 함께 실행 가능한 분류와 불가능한 분류는 각각 63개 버킷을 사용하며 그룹 사이에 의존성 전환이 있다. 원본 작업 이름으로 두 분류를 확인했다.
4. 두 분류의 실행 콜백은 공통 `0xaa31c4`를 호출한다. 이 함수는 명령 길이를 읽어 실제 명령 vtable +0x8을 호출하고 소멸자를 실행한 뒤 블록을 원본 풀로 돌려보낸다. 따라서 차량 UpdateVehicleParams의 등록부터 실제 소비까지 정적 연결이 확보됐다.
5. 이어서 각 장면의 `0x3a54dc`가 기존 중복 제거·객체 갱신·정리 작업을 같은 의존성 컨텍스트에 등록한다.
6. 원본 `RenderFrameTick` 콜백 `0x20869c`는 상위에서 받은 boolean을 `0x209234`로 전달한다. 값이 참일 때 원본 본 이력 갱신 `0x20a958`이 실행된다. 최종 작업 의존성은 명령 소유자의 +0x8에 보관된다.

`0x141b10`은 CPU에서 작업 완료를 기다리는 함수로 해석하지 않는다. 대기 중인 완료 그룹을 다음 작업의 선행 의존성으로 이동시키고 새 그룹을 만든다. `0x14299c`는 선행 작업이 남아 있으면 그 의존성에 콜백을 연결하고, 없으면 스케줄러에 제출한다. 이는 원본 작업 순서를 재사용할 근거이며 모드에서 동기 대기를 추가할 근거가 아니다.

작업 의존성 포인터 자체는 렌더 프레임 번호가 아니다. 상위 boolean의 생성 조건, 실제 호출 주기, 아래 장면 카운터와 GPU 제출 순서를 더 연결해야 렌더 N-1을 판정할 수 있다. 같은 명령 소비 함수를 사용하는 별도 `0x293af4` 경로도 있으며, 그 경로에는 preskin과 같은 interface virtual +0x20 → +0xfa0 접근이 있다. 이를 동일 프레임으로 바로 인정하지 않는다.

## 장면 갱신 카운터와 이전 정점 parity 연결

이전에 view 카운터로만 기술한 +0x28은 원본 장면 객체의 갱신 카운터다. 원본 생성자 `0x8108dc`는 이를 1로 초기화한다. 생성자와 소멸자 `0x37bdac`의 vtable `0x2ad9798`이 같고, 해당 테이블의 +0x58은 기존 배열 확정 함수 `0x79b9f0`이다.

`0x29401c`는 먼저 렌더러 +0x4ca4를 증가시키고 본 갱신 입력을 확정한다. 전달받은 장면 포인터들을 임시 배열로 복사하고 정렬한 뒤, cold 분기 `0x1e4eab4`에서 포인터가 같은 인접 항목을 제거한다. 이후 각 고유 장면의 +0x28을 한 번 증가시키고 virtual +0x58에 렌더러 카운터를 전달한다. 같은 장면이 입력에 여러 번 있어도 이 경로에서 중복 증가하지 않는다.

`0x79b9f0`은 장면 +0x267bb4에 저장한 직전 렌더러 토큰과 비교하여 중복 확정을 건너뛴다. 새 토큰에서는 원본 스냅샷/초기화 함수를 호출하고 append/sealed 배열을 교환한 뒤 유효한 명령 수를 확정한다. 기존 preskin 생산 함수 `0x76c11c`/`0x76d944`와 드로우 접근 함수 `0x23a1a0`의 +0xfa0 → 장면 +0x28 입력을 이 공급부에 연결했다.

이로써 이전 정점 parity와 객체 배열 확정이 같은 원본 장면 갱신 체계에 속함을 정적으로 확인했다. 별도 모드 카운터나 전체 복사를 추가할 근거가 아니다. 다만 입력 목록에 없는 장면은 이 순회에서 증가하지 않는다. 상위 호출자의 장면 선택, 렌더가 생략된 경우, 다중 view, 실제 GPU 입력의 N-1 관계는 아직 미확인이다. 새 MV 또는 실시간 admission 완료로 판정하지 않는다.

## 실제 갱신 호출자와 원본 프레임 전달

PID 24404에서 CPU 메타데이터만 기록하는 한 곳의 진단 훅으로 원본 갱신 75회를 관찰했다. 실제 호출자는 `0x292a54` 안의 `0x292c9d`다. 75회 모두 boolean은 1, 장면 카운터 및 렌더러 카운터의 증가량은 1이었다. 장면 확정 토큰은 갱신 후 렌더러 카운터와 75회 모두 일치했다. 같은 장면의 연속 기록 74쌍에서 앞 기록의 after와 다음 before도 일치했다. 이 기록은 한 장면의 짧은 관찰이며 모든 렌더 조건의 증거가 아니다.

실행 중 렌더러 vtable `0x312aed8`의 +0x450은 `0x18f6e20`이었다. 이 원본 접근 함수는 renderer +0x70의 명령 소유자를 반환한다. 해당 소유자의 vtable `0x2c11958` 및 +0x10/+0x18 대상은 각각 `0x29384c`/`0x293af4`였고 정적 PE 포인터와도 일치했다. 고정 멤버 로드 바로 뒤의 호출만 찾는 초기 검색은 이 접근 함수 경유를 놓쳤다.

`0x292a54`는 프레임 기술 정보의 장면 목록을 `0x29aa68`로 모은다. +0xfa0/+0xfa8/+0xfb0의 null 아닌 참조를 추가하고 중복을 제거한다. `0x292c9d` 호출에는 상수 true를 넘긴다. 호출 뒤 `0x293978`이 같은 프레임 기술 정보를 받아 원본 프레임 객체를 만든다.

원본 할당/생성 `0x293c7c → 0x294c94 → 0x294d2c`는 프레임 객체 +0x10의 데이터에 장면 참조들을 옮기고 원래 슬롯을 비운다. 객체의 virtual +0x20은 `0x18ec810`으로, 이 +0x10 데이터를 반환한다. 따라서 이후 virtual +0x20 → +0xfa0 접근은 앞서 갱신한 장면 참조를 원본 프레임 소유권을 통해 받는다.

`0x293978`은 명령 소유자 +0x18의 `0x293af4`를 호출한다. 원본 작업 의존성 뒤에 `0x293568`이 같은 프레임 객체를 보유하는 `RenderScene/FlushRenderScene` 작업을 등록한다. 콜백 `0xaa3904 → 0xaa39b8`은 작업 컨텍스트 +0x38에 프레임 참조를 보유하고 `0x219730`에 전달한다. 해당 함수의 virtual +0x20 → +0xfa0가 같은 전달 구조다.

상위 호출자와 boolean, 프레임 객체 소유권은 이 경로에서 연결했다. 실제 GPU 생산/소비, view가 여러 개이거나 생략된 경우, 이전 정점이 정확한 렌더 N-1인지와 그룹 원소 대응은 남아 있다. 다른 함수의 virtual +0x20까지 무조건 같은 타입이라고 해석하지 않는다.

진단 DLL은 `scene-tick-probe-0fbd4fdf168b/observer.dll`이며 SHA-256은 `1a20eb96b2b8104a5d09f4be2b5c88e0f4c57192525973754f80e95d1e459ea7`이다. 기존 로더로 실행 중 연결했으며 MO2 제품 DLL은 교체하지 않았다. 기록은 종료했고, 모듈은 프로세스 종료까지 원본 호출을 전달한다. GPU 명령/버퍼 복사 및 새 MV/FG 입력 변경은 없다. 독립 입력 검사와 실제 호출 관찰은 통과했으나 장시간 안정성 판정은 아니다.

## 분석 정정과 미확인 요청 조건

기존 `match_shared_native_motion.py`의 `modifier_key`는 행 번호보다 작거나 같은 가장 가까운 슬롯 이름으로 b7 로드를 표시했다. 캐시 슬롯에는 별도 리소스 주소 공간도 섞여 있으므로 이 방법은 정확하지 않다. 5 VS에서 실제 MotionMatrix의 세 번째 행인 b7[8]이 CullObjectsCB로 잘못 표시됐다.

이번 원본 공급 조사에는 `native_modifier_bindings.py`를 사용한다. 실제 생성자와 원본 writer의 상수 쓰기 범위를 기준으로 b7을 판정하고 리소스 슬롯을 제외한다. 899 VS의 이전 입력을 재추출해 오류 0개, b7 로드 3,512개의 범위 연결을 확인했다. 5개 이름을 정정했으며 전체 VS/PS 수와 기본 공급별 VS 수는 변하지 않았다. 기존 graft/공유 그래프 결과는 이 정정을 반영한 재검증 전까지 제품 적용 근거로 승인하지 않는다. 원본 바이트코드나 게임 입력을 수정한 작업은 아니다.

20 VS의 24개 로드는 선언과 원본 상수 범위는 대응하지만 캐시 request_mask의 해당 모디파이어 비트가 없다. DismParams 6 VS와 의상 IsBound 18 VS가 중첩된다. 해당 VS에는 Discarded 아닌 technique도 있다. 원본 캐시의 요청 마스크와 실제 생성자/선택 조건을 추가 연결해야 하며, 이를 원본 버그나 항상 누락된 실시간 입력이라고 단정하지 않는다.

- `motion-supply-route.json`, `native-preskinned-supply.json`: 기존 공통 MotionMatrix와 이전 정점 공급 증거. 각 문서의 미확인 항목 유지.
- `audit_engine_history_sources.py`, `engine-history-source-audit.json`: 원본 root 이력과 virtual f0의 LOD 선택을 구분. 23개 함수/139개 지시문, 그룹의 16비트 소스 인덱스·현재 변환 재배열·4바이트 LOD 메타데이터 크기 변경을 연결. 원소 수/순번을 시간상 객체 ID로 승인하지 않음.
- `audit_recorded_output_formats.py`, `recorded-output-formats.json`: 기존 전체 PSO 생성 기록 5,309개에서 VS/PS 쌍이 맞는 129개를 추가 출력 조사에 연결. 원본 바이트 51개 해시 재검증. 투명 타깃 2의 R8/미선언 및 추가 G-buffer 타깃 3의 조건별 형식을 구분. 실제 실행·후속 소비는 미확인.

- `audit_native_camera_history.py`, `native-camera-history.json`: 원본 함수 23개/지시문 135곳과 두 PS. 카메라 이력 저장 후 현재 갱신, 같은 프레임의 view 선택·노드 전달, 초기화 생성자/vtable, depth·b6·velocity 바인딩 및 출력 식. 객체 입력 없음. 실제 graph 실행/GPU N-1은 미확인.

제품 코드 또는 설치 DLL의 새 적용은 수행하지 않았다. 정적 공급 연결, 실시간 입력 검증, 전체 화면 MV 출력, FG 개선 검증은 별개 통과 단계다.
