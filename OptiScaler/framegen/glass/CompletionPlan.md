## 사용자가 요청한 작업

불투명 물체의 원본 MV 생성 경로 전체를 먼저 조사한다. 실제 MV 출력에서 셰이더 계산, 바인딩, 이전 정보의 생산·보존, 실행 조건까지 역추적하여 공통 로직과 예외를 정리한다. 그 다음 투명 객체의 실제 렌더 입력을 원본 경로에 대조하고 재사용한다. 투명 객체의 모든 상태를 이미 파악했다고 가정하지 않는다. 배열은 원본 조사에 포함되는 한 항목이다. 중간까지 확인한 후보를 추정으로 구현하지 않는다.

불투명 경로의 구현을 우선 조사하되 모든 상태에 원본 MV가 반드시 존재한다고 단정하지 않는다. 공급이 없거나 패스가 제외되는 경우도 생산자·선택 조건을 추적하여 근거를 남긴다. 그 확인을 마친 뒤 필요한 보완만 설계한다.

최종 결과는 실제 객체와 원본 메시/재질에서 얻은 정확한 화면상 경계 및 현재/직전 프레임 위치를 사용하는 게임 모드다. 영상 추정, 카메라 이동만의 대체, 일부 컵/식생 성공으로 완료하지 않는다. 경계는 객체 MV를 사용하고, 내부는 재질 투과율에 따른 조절 가능한 가중치를 사용한다. 중첩은 카메라에 가까운 표면을 우선한다. 실제 FG에서 배경 부착과 경계 침범이 개선되어야 한다.

## 확인된 상태와 미확인 상태

[원본 MV 경로표](NativeOpaqueMvRoutes.md)에 출력, 공통 공급원, 상태별 미확인 지점과 다음 확인 위치를 유지한다. 본 버퍼의 원본 링 소유/이전 구간 선택/메타데이터 기록/공통 슬롯 10 바인딩을 정적으로 연결했다. 이는 정확한 렌더 N-1과 모든 상태의 GPU 바인딩을 확인했다는 뜻은 아니다.

| 항목 | 현재 증거 | 판정 |

## 실행 순서와 통과 조건

### 1. 불투명 물체의 모든 원본 MV 생성 경로 역추적 — 현재 단계

아래 순서가 이 단계의 필수 순서다. 기존 투명 상태 분류는 이후 대조용 자료로만 사용한다.

1. 불투명 물체의 실제 MV 출력과 이를 기록하는 패스/셰이더부터 조사한다. 기존 879개 velocity VS는 초기 자료이며 전체 생성 경로라고 선언하지 않는다. PS 출력, 별도 compute/생성 패스, 패스 선택, 실제 MV 리소스 생산 관계를 조사하여 누락을 확인한다.
2. 각 출력에서 현재·이전 위치 계산, 업로더/바인딩, 입력 생산자, 보존·갱신 시점까지 끝까지 역추적한다. 데이터가 없으면 상위 생산/선택 조건까지 확인한다.
3. 원본 조사 결과로 일반 객체, 병합 드로우, 배열, 스키닝, 의상, 차량, 파괴, 입자, 절차적 변형 등의 공통 경로와 예외를 정리한다. 미분류 항목을 유지한다. 객체 대응, 수명, 재배열, 프레임 전환까지 포함한다.
4. 원본 경로표와 실제 바인딩/MV 결과의 검증을 마친 뒤 투명 입력과 대조한다. 재사용할 함수/리소스/계산과 필요한 최소 변경을 확정한 후 구현한다.

이후 투명 입력 대조 시 확인할 세부 항목:

1. 투명 경로의 전체 인벤토리를 객체 저장 상태와 위치 변형 방식으로 분류한다. 단일 객체, 독립 프록시의 드로우 병합, 원소 배열, 스키닝/단일 본/preskinned, 의상, 차량, 파괴, 입자, 빌보드/리본, 절차적 변형과 LOD 전환을 포함한다. 이 분류들은 중첩될 수 있으며 현재 장면에 없는 경로도 남긴다.
2. 각 상태에 대응하는 불투명 및 원본 velocity 경로를 찾는다. 모든 원본 velocity VS에서 이전 clip 위치의 데이터/제어 의존성을 추출하고 PS의 실제 MV 출력까지 연결한다. 현재 위치 그래프 일치를 이전 위치 증거로 사용하지 않는다.
3. 각 입력을 현재/이전 원소별 변환, 공통 MotionMatrix, 이전 본, 이전 정점, 입자 상태, 시간/절차적 변형, 기타 리소스로 구분한다. 각 경로에서 실제 객체/원소 → 생산자 → 보존/갱신 → 그룹 선택/재배치 → 업로더/바인딩 → VS 이전 출력 → PS MV 출력을 추적한다.
4. 원본이 배열을 그대로 쓰는지, 분할해서 그리는지, 카메라 성분만 쓰는지, 특정 조건에서 제외하는지 확인한다. 정지/이동, 생성/삭제, 재배열, 변형, LOD, 렌더 프레임 전환 조건도 연결한다. 이름/드로우 수만으로 판단하지 않는다.
5. 투명 경로와 원본 MV 경로의 차이를 공급 플래그, 리소스, 바인딩, 셰이더, 패스 선택별로 기록한다. 공급부가 보이지 않으면 그 입력의 생산자와 상위 선택 조건까지 올라간다. 이미 검증된 플래그/모디파이어는 변경 또는 모순이 없으면 증거를 재사용한다.
6. 같은 위치/공급 로직을 쓰는 상태는 묶고 진짜 예외만 분리한다. 전체 대응표를 검토하여 공통 재사용 지점, 추가해야 하는 입력, 별도 처리가 필요한 상태를 확정한 후 2단계로 진행한다.

산출물: 아래 열을 갖춘 상태별 공급·계산 대응표와 원본 코드/캡처 근거. 각 셀은 확인/미확인/원본 미제공을 구분한다. 원본 미제공 판정에는 상위 생산자/선택 조건의 근거가 필요하다.

| 필수 열 | 기록할 내용 |
| --- | --- |
| 상태와 적용 범위 | 저장 방식, 변형 방식, 해당 렌더 경로 및 다른 상태와의 조합 |
| 원본 기준 경로 | 대응하는 기존 MV 경로와 실제 코드/셰이더 위치 |
| 현재·이전 입력 | 소유자, 생산자, 보존·갱신 시점, 수명 및 N-1 근거 |
| 객체·원소 대응 | 원본 인덱스, 재배열/분할/병합 처리, 스키닝·파괴 대응 |
| GPU 공급과 계산 | 업로더, 바인딩, 선택 조건, VS와 PS의 실제 계산 |
| 투명 경로 차이 | 누락 플래그/입력/패스와 필요한 최소 변경 |
| 재사용안과 비용 | 공통 함수/리소스/셰이더 재사용, 추가 복사·연산·메모리 |
| 검증과 잔여 항목 | 정적 근거, 실제 입력/출력 증거, 다음에 확인할 정확한 지점 |

통과 조건: 원본 MV 생산 경로의 조사 범위와 누락 검사가 명시되고, 확인한 모든 경로의 공급부터 출력까지 공통 로직과 예외가 근거로 연결되어야 한다. 그 이후 투명 입력과의 대응 및 미대응 항목을 정리한다. 조사되지 않은 셀을 상상으로 채우지 않는다. 단순 후보 목록, 고정 객체, 셰이더 컴파일만으로 통과하지 않는다. 이 단계에서는 조사에 필요한 최소 진단만 추가하며, 미확인 공급 구조를 전제로 제품용 캐시·셰이더·훅을 확장하지 않는다.

### 2. 확인한 원본 경로를 투명 입력에 연결

원본 공급 조건/모디파이어와 기존 변형 계산을 우선 재사용한다. 실제로 없는 입력에만 보완 로직을 만든다. 객체 생성·해제·배열 교체·중복 요청 제거·원본 그룹 선택을 함께 적용한다. 게임 업데이트 단위와 렌더 프레임을 구분하고 현재/N-1 제출을 연결한다.

산출물: 원본 경로와 투명 경로의 대응 코드, 실제 입력 확보/누락 사유 카운터, 연속 프레임 비교.

통과 조건: 카메라와 객체 자체 이동, 독립 이동 원소, 스키닝/파괴/절차적 경로에서 다른 원소나 오래된 입력을 쓰지 않는다. 같은 공급 구조는 한 어댑터로 처리하며 객체 이름 목록으로 선택하지 않는다. 미지원 경로가 남으면 전체 완료로 표시하지 않는다.

### 3. 실제 메시/재질로 전체 화면 경계와 MV 생성

원본 정점 변형, 인스턴싱, 재질 discard/coverage, 가시성 조건을 유지한다. 경계는 삼각형의 내부 선이 아니라 화면상 객체/재질 영역의 외곽이다. 색상 영상의 에지 검출로 추정하지 않는다. 실제로 래스터화된 객체 영역에서 내부 방향 경계 폭을 계산할 수 있다.

가장 가까운 투명 표면의 깊이/MV/재질 정보를 함께 선택한다. 경계 가중치는 1, 내부 가중치는 실제 불투명도 a에 대해 `saturate(gain*a+bias)`를 초기 구현으로 사용한다. RGB 투과율을 스칼라 a로 만드는 계약은 해당 재질 출력 의미를 검증한 뒤 정한다. 합성식은 `w*objectMV + (1-w)*originalMV`이며 경계 폭/gain/bias를 설정으로 노출한다. 이 식의 FG 효과는 다음 단계에서 검증한다.

산출물: 같은 프레임의 전체 화면 색상, 객체 영역/깊이, 경계, 객체 MV, 원본 MV, 최종 MV, 수치 차이 및 누락 지도.

통과 조건: 실제 변경된 MV가 객체의 이동 방향/크기에 맞고, 창문 내부 배경 전체를 표면 운동으로 덮지 않는다. 서로 다른 해상도/유효 영역은 정규화 좌표와 원본 MV 스케일/부호/지터 계약으로 처리한다.

### 4. 실제 DLSS FG 입력과 생성 프레임 검증

기존 가벼운 FG 재생 도구에 실제 게임 FG 입력과 객체 버퍼를 동일 프레임으로 제공한다. 정지 투명체 뒤의 독립 이동 배경, 카메라 이동, 투명체 자체 이동, 중첩, 생성/소멸을 비교한다. 2배와 4배의 실제 생성 프레임을 직접 검사한다. 재생의 내부 상태가 게임과 같지 않다면 그 한계를 명시한다.

통과 조건: MV가 바뀐 사실과 FG 고스팅 개선을 각각 검증한다. 전체 화면 및 문제 영역에서 배경 부착/경계 침범/새 왜곡을 비교한다. 단일 MV의 한계가 남으면 이를 숨기지 않고, 기존 범위 내 후속 보정 방향을 근거와 함께 결정한다.

### 5. 효율화·호환성·설정 상태 표시

원본 GPU 리소스와 순서를 재사용하고 매 프레임 전체 CPU readback, 메모리 검색, 셰이더 컴파일, 대기 동기화를 제품 경로에서 제외한다. 캐시는 바이트/항목 상한과 수명 무효화를 가진다. 추가 드로우·픽셀 연산·복사량을 집계한다. 약 1ms는 설계 목표이며 미측정 보장을 하지 않는다.

OptiScaler 모듈 경계를 유지하고 기존 version.dll/ASI MFG 해제 경로를 재구현하지 않는다. 상태창/로그는 후킹, 객체 입력, N-1, 경계 출력, 실제 FG 입력 교체, 우회 사유를 구분한다. 기존 비동기 GPU 타이머를 재사용한다. 실행 파일 변경은 구조 검증으로 판정하고 드라이버 고정 주소는 사용하지 않는다.

### 6. MO2 적용 및 최종 완료 판정

빌드/관련 검사 후 백업과 해시를 기록하고 MO2 모드에 배치한다. 가능하면 기존 교체형 호스트에서 검증한다. 재시작이 필요하면 이유와 준비된 변경을 먼저 기록하고 사용자에게 한 번 요청한다.

통과 조건: 실제 로드된 DLL과 설정, 원본 MFG 동작, 전체 투명 경로 지원표, 실제 FG 입력 교체 및 생성 프레임의 개선을 확인한다. 일부 객체·독립 검사·후킹 성공만으로 goal을 완료하지 않는다.

### 7. 게임 재시작 없는 실험 경로

상주 모듈 코드를 바꾸면 프로세스 재시작이 필요하다. 그 밖의 실험은 재시작 없이 파일 채널로 처리한다. `Glass\glass-debug.request`에 한 줄 명령을 쓰고 `Glass\glass-debug.response`를 읽는다. 상태 확인은 `status`, 경계 디스패치 토글은 `packed=on|off`, 행 수는 `rows=N`, 가장자리 폭은 `edge=N`, 내부 불투명도 임계는 `opacity=N`이다. `soft-reload`는 네이티브 FG 기록을 retire한 뒤 다음 평가에서 재승인하고 packed 카운터를 초기화한다. `reload-shader`는 `Glass\GlassObjectMotion.hlsl`을 디스크에서 다시 컴파일한다. 도구는 `glass-live-tools/glass-ctl.ps1`이다.

월드 객체 재등록이 필요한 실험은 게임 안 Load Game으로 처리한다. 설치된 프레임워크 중 RedHotTools의 리로드 계열은 redscript·TweakDB·아카이브 자료용이고, red4ext는 GameState 콜백만 제공하며, CET는 자체 Lua 모드만 리로드한다. 상주 DXGI 모듈이나 엔진 렌더 상태를 재시작하는 기능은 없다.

TDR 원인은 새 GPU 작업과 FG 입력 교체를 분리해서 판정한다. `GlassFG/PackedSubstitute`(기본 false)와 명령 `substitute=on|off`, `probe`, `apply`가 그 경로다. `probe`는 packed 디스패치를 rows=240으로 켜고 입력 교체를 끈 상태로 둔다. TDR이 없으면 `apply`로 입력 교체를 켠다. 같은 실행 안에서 두 단계를 오갈 수 있으므로 재시작 없이 원인을 특정한다.
